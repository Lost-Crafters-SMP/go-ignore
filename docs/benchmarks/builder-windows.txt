# Incremental Builder versus one-shot Compile

Date: 2026-10-10. Go 1.27.1, windows/amd64, AMD Ryzen 7 5800X3D, one logical
CPU (affinity mask 0x40), six 1-second samples per benchmark, test.cpu=1,
benchstat from the isolated bench module. Workloads follow the incremental
builder contract review: a 1,000-rule root source plus 32 discovered sources
of 20 rules each — nested scopes (d, d/d, ...), sibling branches, repeated
same-scope additions, insertions below RankCommand, successively higher ranks
and mixed-depth sibling traversal. Every comparison uses equivalent complete
source sets.

## One-shot Compile: extracted-compiler code versus previous code

B/op and allocs/op are identical on every shape (nested/siblings/mixed
564,673 B / 220 allocs; same 540,649 B / 78; command 564,688 B / 221; higher
540,649 B / 78). A first long unattended run reported command +68% and higher
+29% sec/op; interleaved same-window reruns of both binaries did not reproduce
them (command 249 us new vs 245 us old, higher 254 us vs 272 us). Matching
rows whose timed code is byte-identical in both binaries differed by +2% to
+13% in that same long run, establishing the between-run noise floor.

## Incremental construction (same binary, same window)

| Shape | Compile | 32 additions | Factor | B/op delta |
| --- | ---: | ---: | ---: | ---: |
| nested | 273.0 us | 356.4 us | 1.31x | +4.0% |
| siblings | 269.8 us | 308.5 us | 1.14x | +4.0% |
| same | 256.4 us | 301.5 us | 1.18x | +4.3% |
| command | 273.5 us | 301.9 us | 1.10x | +4.1% |
| higher | 256.2 us | 306.3 us | 1.20x | +4.3% |
| mixed | 288.6 us | 415.5 us | 1.44x | +4.8% |

Single-batch builder (one Add of the complete set): +2.5% to +2.9% B/op;
allocs 224 vs 220 (nested-like shapes) and 77 vs 78 (same-scope; lazily
created literal maps can allocate fewer objects); sec/op differences not
statistically significant.

Allocation objects for 32 separate additions: 405 vs 220 (nested, siblings),
265 vs 78 (same, higher), 410 vs 221 (command), 408 vs 220 (mixed) — roughly
six objects per 20-rule batch (batch rule slice, arena chunk tails, scratch
growth), with no temporary delta matchers or delta indexes.

## Matching and descent: builder-built versus compiled matcher

Allocation counts and bytes are identical on every workload (0 B / 0 allocs;
blocking 24 B / 1 alloc). The long run showed literal +6.1% (3.4 ns),
nested-hit +3.8% and higher-miss +5.2%; a ten-sample rerun inverted every
difference (literal 60.0 ns builder vs 61.8 ns compiled, nested-hit 2.77 vs
2.88 us, higher-miss 3.32 vs 3.40 us). Sub-10% match deltas on this host are
noise; the zero-allocation hot path is preserved and no reproducible matching
regression exists.

## Retained heap (post-GC HeapAlloc deltas; four trials, spread under 100 B)

| Shape | Compile | Builder built | Builder live (still open) |
| --- | ---: | ---: | ---: |
| nested | 553,968 | 542,944 (-2.0%) | 547,520 |
| command | 554,192 | 543,216 (-2.0%) | 547,792 |
| same | 535,792 | 524,576 (-2.1%) | 527,528 |
| siblings | 554,176 | 542,912 (-2.0%) | 547,520 |

Builder-built matchers retain slightly less than one-shot compilation because
per-scope literal maps are created lazily instead of eagerly for both kinds.

Reproduce with `BenchmarkBuilderConstruction` and `BenchmarkBuilderMatch`
(mise exec -- go test . -run '^$' -bench '^BenchmarkBuilder' -benchmem), or
re-run the review-shaped suites from the contract-review overlay methodology.
